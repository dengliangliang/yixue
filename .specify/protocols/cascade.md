# Cascade 开发流程协议

> **版本**: 1.0  
> **最后更新**: 2025-01-19  
> **适用范围**: 1213易学算命小程序项目

## 1. 协议概述

本协议定义了使用 AI 辅助开发时的标准流程和规范，确保开发过程可控、可追溯、高质量。

### 1.1 核心原则
1. **AI 绝不自作主张**: 所有决策通过寸止MCP确认
2. **文档先行**: 先写规格，再写代码
3. **TDD驱动**: 测试先行，红绿重构
4. **知识沉淀**: 及时更新知识库

### 1.2 适用场景
- 新功能开发
- Bug修复
- 代码重构
- 性能优化

## 2. Spec Kit 工作流

### 2.1 流程概览

```
/speckit.specify
    ↓
/speckit.clarify (可选)
    ↓
/speckit.plan
    ↓
/speckit.tasks
    ↓
/speckit.implement
    ↓
/speckit.analyze (可选)
    ↓
/speckit.checklist
    ↓
/speckit.review
```

### 2.2 命令详解

#### 2.2.1 /speckit.specify - 生成规格说明
**目的**: 创建功能规格文档

**输入**: 功能需求描述

**输出**: `specs/NNN-feature/spec.md`

**检查点**:
- [ ] 需求描述清晰
- [ ] 验收标准明确
- [ ] 技术约束已列出
- [ ] 依赖关系已识别

**AI行为**:
1. 分析需求
2. 生成规格文档
3. 通过寸止询问是否需要澄清

#### 2.2.2 /speckit.clarify - 澄清需求
**目的**: 解决需求中的模糊点

**输入**: 需要澄清的问题

**输出**: 更新 `spec.md`，生成 `clarification-report.md`

**检查点**:
- [ ] 所有疑问已解答
- [ ] 规格文档已更新
- [ ] 变更已记录

**AI行为**:
1. 识别模糊点
2. 通过寸止提问
3. 根据回答更新文档

#### 2.2.3 /speckit.plan - 制定实施计划
**目的**: 设计技术方案

**输入**: `spec.md`

**输出**: 
- `plan.md` - 实施计划
- `data-model.md` - 数据模型
- `research.md` - 技术调研
- `contracts/` - 接口契约

**检查点**:
- [ ] 技术方案可行
- [ ] 数据库设计合理
- [ ] API设计符合规范
- [ ] 已参考现有代码

**AI行为**:
1. 阅读 constitution.md
2. 阅读相关知识库文档
3. 参考现有代码实现
4. 生成技术方案
5. 通过寸止确认方案

#### 2.2.4 /speckit.tasks - 生成任务清单
**目的**: 分解实施任务

**输入**: `plan.md`

**输出**: `tasks.md`

**检查点**:
- [ ] 任务粒度合适
- [ ] 依赖关系清晰
- [ ] 工时估算合理
- [ ] 优先级明确

**AI行为**:
1. 分解任务
2. 标注依赖关系
3. 估算工时
4. 通过寸止确认任务清单

#### 2.2.5 /speckit.implement - TDD实施
**目的**: 按照TDD流程实现功能

**输入**: `tasks.md`

**输出**: 代码文件和测试文件

**TDD流程**:
1. **Red**: 编写测试用例（失败）
2. **Green**: 编写实现代码（通过）
3. **Refactor**: 重构优化代码

**检查点**:
- [ ] 测试用例先于实现代码
- [ ] 测试覆盖率 > 80%
- [ ] 所有测试通过
- [ ] 代码符合规范

**AI行为**:
1. 阅读已有测试用例和公共测试方法
2. 阅读知识库测试模板和规范
3. 生成测试用例
4. 通过寸止展示测试用例
5. 用户审核通过后生成实现代码
6. 使用 desktop-commander MCP 执行测试
7. 根据测试结果修复问题

**测试执行**:
```bash
# 使用 desktop-commander MCP 非阻塞执行
# 最多等待30秒
php think unit TestClassName
```

#### 2.2.6 /speckit.analyze - 一致性验证
**目的**: 验证跨文档一致性

**输入**: 所有相关文档和代码

**输出**: `analysis-report.md`

**检查内容**:
- [ ] 代码与文档一致
- [ ] 数据库结构与设计一致
- [ ] API实现与契约一致
- [ ] 测试覆盖所有需求

**AI行为**:
1. 对比文档和代码
2. 检查数据库结构
3. 验证API实现
4. 生成分析报告
5. 通过寸止报告问题

#### 2.2.7 /speckit.checklist - 质量检查
**目的**: 执行质量检查清单

**输入**: 实现的代码

**输出**: `checklist-report.md`

**检查清单**:
- [ ] Constitution 合规检查
- [ ] 代码风格检查
- [ ] 安全性检查
- [ ] 性能检查
- [ ] 文档完整性检查

**AI行为**:
1. 逐项检查清单
2. 记录检查结果
3. 通过寸止报告问题

#### 2.2.8 /speckit.review - 代码审查
**目的**: 进行代码审查

**输入**: 实现的代码

**输出**: 审查意见

**审查内容**:
- 代码质量
- 设计模式
- 性能优化
- 安全隐患

**AI行为**:
1. 分析代码
2. 提出改进建议
3. 通过寸止展示审查结果

## 3. 强制规则

### 3.1 文档规则
- ❌ 不生成总结性文档（除非明确要求）
- ❌ 不生成报告文档（除非流程要求）
- ✅ 只生成 Spec Kit 流程中明确要求的文档

### 3.2 代码规则
- ✅ 必须先生成测试用例
- ✅ 必须等待用户审核测试
- ✅ 必须执行测试验证
- ❌ 不要在代码中添加 emoji
- ❌ 不要使用重试机制
- ❌ 不要使用降级处理

### 3.3 数据库规则
- ✅ 必须使用 prepareParam() 参数化查询
- ✅ 必须使用静态方法调用事务（Db::begin/commit/rollback）
- ✅ 必须捕获 \Throwable 异常
- ❌ 不要直接修改 huodong.sql
- ✅ 提供增量 SQL 文件给用户执行

### 3.4 前端规则
- ✅ 必须只使用 class 选择器
- ❌ 不要使用通配符选择器 *
- ❌ 不要使用标签选择器（p, div等）
- ✅ 必须使用中文注释

### 3.5 测试规则
- ✅ 必须真实连接数据库（不使用空mock）
- ✅ 必须考虑业务集成测试
- ✅ 必须考虑各种边界情况
- ❌ 不要设置跳过测试标识
- ✅ 集成测试同样需要执行测试命令

### 3.6 部署规则
- ❌ 不要在服务器直接创建业务代码文件
- ✅ 必须在本地创建后上传
- ❌ 不要自动提交到 GitHub（除非明确指令）
- ✅ 测试代码可以在服务器创建

## 4. 寸止交互规范

### 4.1 必须使用寸止的场景
1. 需求不明确时
2. 存在多个方案时
3. 计划变更时
4. 任务完成前
5. 发现问题时

### 4.2 寸止交互格式
```markdown
# 标题

## 当前状态
简要说明当前进度

## 问题/选项
列出问题或选项

## 建议
AI的建议（如有）

---
请选择或提供指示
```

### 4.3 禁止的行为
- ❌ 直接在对话中询问用户
- ❌ 自行决定技术方案
- ❌ 未经确认就结束任务
- ❌ 跳过测试步骤

## 5. 知识库管理

### 5.1 知识库结构
```
.knowledge/
├── index.yaml              # 知识库索引
├── features/               # 功能模块文档
│   └── feature-name/
│       ├── README.md       # 模块说明
│       ├── database.md     # 数据库设计
│       ├── code-map.md     # 代码地图
│       └── tests.md        # 测试文档
└── adr/                    # 架构决策记录
    └── NNN-title.md
```

### 5.2 更新时机
- 新功能实现后
- 重大架构变更后
- 发现重要模式后
- 修复重要Bug后

### 5.3 文档质量要求
- 清晰准确
- 及时更新
- 包含示例
- 标注版本

## 6. 测试规范

### 6.1 测试类型
1. **单元测试**: 测试单个方法
2. **集成测试**: 测试业务流程
3. **功能测试**: 测试完整功能

### 6.2 测试命名
```php
// 单元测试
public function testMethodName()

// 集成测试
public function testUserCanCreateRecord()

// 功能测试
public function testCompleteCalculationFlow()
```

### 6.3 测试数据
- 使用真实数据库
- 准备测试数据
- 清理测试数据

### 6.4 测试执行
```bash
# 执行所有测试
php think unit

# 执行特定测试类
php think unit TestClassName

# 执行特定测试方法
php think unit TestClassName::testMethodName
```

## 8. 版本控制

### 8.1 分支策略
- `main`: 生产环境
- `develop`: 开发环境
- `feature/xxx`: 功能分支

### 8.2 提交规范
```
[模块] 简要说明

详细说明（可选）

相关Issue: #123
```

### 8.3 合并流程
1. 功能分支开发
2. 提交代码审查
3. 通过测试
4. 合并到develop
5. 测试通过后合并到main

## 9. 故障处理

### 9.1 发现Bug
1. 记录Bug现象
2. 分析根本原因
3. 编写测试用例（复现Bug）
4. 修复Bug
5. 验证测试通过
6. 更新文档

### 9.2 回滚流程
1. 备份当前状态
2. 恢复到上一版本
3. 验证功能正常
4. 分析失败原因
5. 制定修复计划
